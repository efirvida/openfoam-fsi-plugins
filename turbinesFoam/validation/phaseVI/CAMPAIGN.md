# Phase VI rotational-augmentation validation campaign (prepared only)

Converged power-curve campaign for the **rotational-augmentation candidate**:
the full staged curve at D/32 plus a D/48 spot-check, for the three models
`alm`, `asm` and `asm-mesh`, in **two physics arms** so each model is evaluated
at both Glauert root-effect settings with data.

> **Prepared only.** The array is never submitted by the preparing change.
> It refuses to run without `TURBINE_LONG_QUEUE_AUTHORIZED=1` (exit 5). The
> launch order stays with the maintainer.

## Arms

| Arm | Rotational augmentation | Glauert root effect | Runner flags | Role |
|---|---|---|---|---|
| **A** (candidate) | on | off | `--rotational-augmentation on --root-effects off` | the proxy candidate |
| **B** (root-on) | on | on | `--rotational-augmentation on --root-effects on` | isolates the root effect at aug-on |
| **control** | off (committed) | on (committed) | `--rotational-augmentation off --root-effects on` | the 2026-09-21 baseline physics |

Dynamic stall off, tip effect on and the Du–Selig `a=b=d=1` constants are the
committed values in every arm. The three variants mirror the committed 0.25-rev
proxy matrix (`scripts/proxyRotationalAugmentation.py`): arm B vs control
isolates the augmentation at root-on, arm A vs arm B isolates the Glauert root
effect at augmentation-on. Arm A is the `augmentation-on + root-off` setting
that the proxy identified as the only one inside the ±15 % band at 7 m/s
(deficit −14.99 % → +1.79 %; archived change
`openspec/changes/archive/2026-09-24-rotational-augmentation/archive-report.md`).
The proxy's own U13 primary criterion was **not** met (augmentation-on `cp`/`ct`
≈ 0, strictly negative), which is exactly why this converged campaign is the
real gate (archive-report finding **C-1**).

`runPhaseVI.sh --restart --run` at a time, and restarts every run from its
latest written time.

Totals: coarse D/32 = 3 models × 5 speeds × 2 arms = **30 runs**; fine D/48

Per-run invocation (the task list is generated by `task_runs` in the array):

```sh
scripts/runPhaseVI.sh -m <model> -u <speed> -mesh <coarse|fine> -s H \
    --rotational-augmentation <on|off> --root-effects <on|off> \
    --run-label <arm label> --restart --run
```

### Arm-separated run directories (`--run-label`)

The runner's run id does **not** encode the augmentation/root state, so both
arms of the same `(model, speed, mesh)` would render into the same
`runs/<model>-U<speed>-<mesh>` directory; `--restart` would then continue from
the *other* arm's physics. The campaign therefore passes
`--run-label <arm label>`, which appends `-<label>` to the run id and records it
in `run.json`:

| Arm | Label | Example run directory |
|---|---|---|
| A | `aug-on-root-off` | `runs/alm-U13-coarse-aug-on-root-off` |
| B | `aug-on-root-on` | `runs/alm-U13-coarse-aug-on-root-on` |
| control | `aug-off-root-on` | `runs/asm-mesh-U7-coarse-aug-off-root-on` |

The run directory is thus the config provenance for its arm (the augmentation
and root state are also recorded indirectly through the rendered
`system/fvOptions`).

### Failure policy (continue-on-error)

Every run is independent, so the task **continues** after a failed run instead
of aborting the remaining runs. Each run's console output is captured to a
per-run log under `runs/campaign-logs/<job>.<task>.<run>.log` (the solver's own
`log.decomposePar` / `log.pimpleFoam` stay in the run directory). If any run
failed, the task prints `Array task <id> summary: <n>/<m> run(s) failed: ...`
and exits **1**; otherwise it exits 0. A re-submission of the same array is
safe: each run re-renders and `--restart` is a no-op once a run has reached
`endTime`, so only the incomplete or failed runs make progress.

## Resource sizing (30k cells/core heuristic)

The user's rule of thumb is ≈30k cells per core. For this case (cell counts
from `config/case.yaml`, the same numbers `tools/case_config.py` validates):

| Mesh | Block product | Cells | Cells/rank at 48 ranks |
|---|---|---|---|
| coarse D/32 | 382 × 168 × 104 | 6,674,304 | 139,048 |
| fine D/48 | 573 × 252 × 156 | 22,525,776 | 469,287 |

The coarse mesh is **6,674,304 cells** — the `153 × 80 × 80 ≈ 0.98 M` estimate
is not the committed block product; the real product is 382 × 168 × 104 (the
`case.yaml` cells, also asserted by the tests). At 30k cells/core the coarse
mesh would need `ceil(6,674,304 / 30,000) = 223` ranks (≈5 nodes) and the fine
mesh `ceil(22,525,776 / 30,000) = 751` ranks (≈16 nodes).

**`--ntasks=48` is kept**, deliberately:

- 48 is the committed decomposition (`decomposition.number_of_subdomains`), and
  the runner requires `--ranks == SLURM_NTASKS`; keeping it matches the
  Stage 1+2 and 2026-09-21 baseline decomposition so a physics delta is not
  confounded with a partition change.
- Both meshes already converged at 48 ranks (Stage 1+2 for D/32, the
  2026-09-21 D/48 mesh-insensitivity check), so 48 is proven feasible.
- The task groups coarse and fine runs, so a single `--ntasks` must cover the
  fine need; 751 ranks would be requested for the 5-run coarse runs too. That
  is a multi-node allocation per task that the prepared-only scope does not
  authorize, and it does not reduce the task count (the submit limit counts
  tasks, not cores).
- The association's `MaxSubmitJobs` is the binding limit here; cores per task
  are not.

So the campaign runs at 139k (coarse) / 469k (fine) cells/rank, i.e. 4.6× /
15.6× above the 30k heuristic, and the 30k target is documented as not met by
design (the committed 48-way decomposition is preferred over ~223/751 ranks).

### Association submit-limit caveat (verified 2026-09-24)

The `leahk/eduardo.donestevez@sequana_cpu` association has
`MaxSubmitJobs=24` and the limit counts **each array task**. The free-slot
count is `24 − (queued jobs)`, so it moves as the queue drains. Two
`sbatch --test-only` probes bracket it:

- at **15 queued** jobs (9 free), the previous 21-task array failed with
  `AssocMaxSubmitJobLimit`; the probe passed at `--array=0-8` (9 tasks) and
  failed at `--array=0-9` (10 tasks);
- at **14 queued** jobs (10 free), the probe passed at `--array=0-9` (10 tasks)
  and failed at `--array=0-10` (11 tasks).

Either way the redesigned **7-task** array fits, whereas the previous 21-task
array did not; it only fails if the association already has **more than 17**
queued jobs. Before launch, re-check the queue (`squeue -u $USER`); if it has
grown past that, either wait or split the array. The array definition itself is
accepted by Slurm: `sbatch --test-only --array=0-6 <script>` reports
*"using 48 processors on nodes sdumont6141 in partition sequana_cpu"* and
creates no job (`squeue -j <id>` → *Invalid job id*).

## Acceptance criteria

Comparison is against the committed Sequence H measurements with the harness
bands **power / torque / thrust ±15 %** (`scripts/comparePhaseVI.py`). Compare
into a **separate `--out`** so the preserved baseline outputs are not
overwritten:

```sh
scripts/comparePhaseVI.py \
    --alm-dir runs/alm-U7-coarse-aug-on-root-off \
    --asm-dir runs/asm-U7-coarse-aug-on-root-off \
    --asm-mesh-dir runs/asm-mesh-U7-coarse-aug-on-root-off \
    --speed 7 --sequence H --out campaign-results/aug-on-root-off/U7-H
```

Repeat per arm and speed (`campaign-results/<arm>/U<speed>-H`); the
`--asm-mesh-dir` argument makes the comparison three-way. The arm directories
differ only in the `--run-label` suffix.

- **In-band curve (primary).** Candidate (arm A) power/torque/thrust inside
  ±15 % of the measured Sequence H curve at the staged speeds — in particular
  the speeds at which the `aug off` baseline failed: 7 m/s (−16 %), 10 m/s
  (−55 %, nonphysical trend) and 13/15 m/s (**negative** power/torque). The
  proxy predicts the 7 m/s deficit closes to ≈ +1.8 % with `root off`; whether
  the high-speed sign flips under augmentation is the open question the
  campaign settles. Arm B reports the same curve at root-on, so the root
  attribution is testable, not assumed.
- **Trend and stall onset.** 10/13/15/25 m/s are URANS deep-stall points: the
  accepted claim is trend and stall onset within the bands, not sub-5 %
  agreement (`README.md` "Modelling limitations").
- **Three-way model form.** `asm-mesh` is compared against `alm`/`asm` of the
  *same arm* to test the model form (distribution difference), not resolved
  chordwise physics (sub-grid caveat, `README.md`). The control arm completes
  the three-way at the committed physics (see the baseline note).

## Baselines and the ASM-mesh gap

- The **ALM/ASM `aug off` Stage 1+2 converged runs (2026-09-21)**, preserved as
  aggregated outputs under `results/U{7,10,13,15}-*-H/` and summarised in
  `results/DIAGNOSIS-2026-09-21.md`, are the control-arm baseline. The
  completed run directories were deleted; the comparison outputs are the
  baseline. The campaign writes its comparisons under `campaign-results/`, so
  these are never overwritten.
- There was **no ASM-MESH `aug off` baseline**. Task 6 adds the 5 ASM-mesh
  coarse control runs (arm control, 7/10/13/15/25 m/s) so the three-way
  model-form comparison at the committed physics is complete; without it the
  three-way at control would have only two of the three models. This closes
  the gap instead of documenting it.
- There is **no 25 m/s baseline output**; for 25 m/s the campaign is
  trend/model-form evidence, not a baseline delta.

## Why the D/48 spot-check is with the NEW physics

The 2026-09-21 **mesh-insensitivity** result (D/32 vs D/48 within 1 % at 7 m/s,
`results/DIAGNOSIS-2026-09-21.md`) was measured with the augmentation **off**
and the Glauert root effect **on** — i.e. it predates the candidate physics.
Neither the Du–Selig stall-delay correction nor the `rootEffects off` ablation
has a mesh-sensitivity result, and the mesh-backed surface is sub-grid by
construction (cells 0.314/0.210 m vs chord 0.218–0.744 m). The spot-check at
7 m/s (attached-flow headline) and 13 m/s (deep-stall collapse) therefore tests
that the new physics is not mesh-dependent; it is a convergence check, not a
re-derivation of the old result. The full curve stays on D/32 (affordable) and
the D/48 pair is a bounded spot-check, not a second full ladder.
